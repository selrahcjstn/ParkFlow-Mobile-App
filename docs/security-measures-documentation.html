1. Executive Summary

ParkFlow Mobile App is an Expo and React Native application for parking-related services. Based on the repository, the system includes user authentication, profiles, vehicle management, document or image uploads, parking reservations and sessions, and real-time notification updates. The app connects to a separate API through Axios and uses SignalR for real-time updates.

The system handles user account information, registration documents, parking activity, and possibly financial or violation-related data. These data types require strong protection against disclosure, tampering, unauthorized access, and service disruption. The app’s most urgent repository-level concern is that the API endpoint is configured with HTTP and the app expressly allows cleartext traffic for iOS and Android. This creates a significant risk for network interception or unauthorized data modification.

The main recommended measures are to enforce HTTPS/WSS for all production traffic, review web token storage, remove or redact sensitive logs, verify backend authorization controls, and validate upload and data-handling protections. These measures should be integrated throughout the Secure SDLC, not added only at the end of development.

It is designed to support a parking service ecosystem that likely includes user accounts, profile data, registration details, scheduling, vehicle information, and real-time status updates. 3. Security Objectives

  • Confidentiality: Only authorized users and staff should access personal, vehicle, registration, and reservation data.
  • Integrity: Data must not be modified, deleted, or manipulated by unauthorized users.
  • Availability: The system should remain available when needed for legitimate users.
  • Authentication: The system must verify user identity and protect session state.
  • Authorization: Users should have only the permissions appropriate to their roles.
  • Accountability: Security-relevant actions must be logged and traceable.
  • Privacy: Personal and sensitive information must be limited, protected, and retained appropriately.

9. Secure System Design

The secure system design should include HTTPS/WSS, API-level authentication, role-based authorization, protected storage, monitored logs, and verified backups. Client-side controls are useful but not sufficient; server-side checks must remain authoritative.

  • Users connect via secure mobile or web client.
  • Web and mobile clients use TLS-protected API and SignalR traffic.
  • API validates identity and authorizes every request.
  • Database and file storage are restricted and encrypted.
  • Audit logs capture events and access without exposing secrets.
  • Backups are protected, tested, and recoverable.

10. Authentication and Authorization

Authentication should verify user identity with secure token validation and, where appropriate, MFA for privileged roles. Authorization should enforce least privilege and ownership checks. The app should not trust client-side UI restrictions as the sole control.

11. Data Security

Data at Rest

Database and file storage should be restricted, encrypted, and backed up securely. Session tokens should be stored using native secure storage and protected against unauthorized access. Any token fallback on web should be reviewed for XSS exposure.

Data in Transit

All production API and SignalR connections should use HTTPS/WSS with valid certificate verification. Cleartext traffic must be disabled in production. The reviewed configuration currently contradicts this requirement.

Password Security

Passwords should not be stored in plaintext. If password-based authentication is used, the backend must hash passwords using a modern, salted password-hashing algorithm. Do not include actual credentials in documentation or screenshots.

12. Secure Coding Practices

  • Validate all inputs at the API boundary.
  • Use parameterized database queries or safe ORMs.
  • Perform server-side authorization checks on every route.
  • Handle errors without exposing stack traces or sensitive messages.
  • Protect sessions, tokens, and refresh flows.
  • Validate file types, sizes, and names before upload.
  • Keep secrets outside source files, build output, logs, and client configuration.
  • Scan and update dependencies regularly.

13. Secure Development / Implementation

Source Code Management

Protected branches, pull requests, and peer review should be required for all sensitive changes. The repository should enforce controlled access and avoid direct commits to critical branches.

Secrets Management

Use a dedicated secret manager for API keys, signing secrets, and release credentials. GitHub Actions environment secrets should be protected and limited to the workflows that require them. Values must never be hardcoded into application code or repo history.

Dependency Management

Use package-lock / version pinning and dependency scanning. Review security advisories and update vulnerable packages promptly. Old or unmaintained libraries should be prioritized for replacement.

14. Security Testing

Before deployment, the project should perform security tests covering authentication, authorization, input validation, file upload, API abuse, and transport protections.

  • Authentication testing: invalid and expired tokens, password reset, session expiry, MFA checks where relevant.
  • Authorization testing: verify that users cannot access data or actions outside their permissions.
  • Input validation testing: injection attempts, malformed IDs, oversized payloads, and unexpected data formats.
  • Upload testing: blocked file extension, oversized files, malicious names, and unauthorized retrieval.
  • API testing: invalid requests, rate limiting, permission boundaries, and token misuse.

16. Secure Deployment

Production deployment should use hardened infrastructure, separate credentials, restricted network access, and verified configuration. Do not deploy with debug settings enabled or secrets embedded in source or build output. Verify the final environment before release and monitor immediately after deployment.

  • HTTPS enabled
  • Default credentials removed
  • Debug mode disabled
  • Secrets removed from source
  • Database access restricted
  • Unnecessary services disabled
  • Backups configured
  • Logging enabled
  • User permissions reviewed
  • Security testing completed

17. Security Monitoring and Logging

Security events should be logged for successful and failed logins, password changes, privilege changes, and administrative actions. Logs must be protected from tampering and restricted to authorized personnel. Suspicious activity should trigger alerts and escalation procedures.

18. Incident Response Plan

  1. Preparation: define roles, contact paths, backup procedure, and escalation rules.
  2. Detection and analysis: determine outage or compromise scope, affected systems, and data exposure.
  3. Containment: disable compromised accounts, isolate systems, and block malicious traffic.
  4. Eradication: remove malicious code or misconfigurations, patch vulnerabilities, and reset credentials.
  5. Recovery: restore verified backups and monitor closely after recovery.
  6. Lessons learned: document cause, impact, and future preventive measures.

19. Backup and Recovery

The project should maintain a documented backup and restore strategy. Data backups should be encrypted, access-controlled, and tested regularly. Recovery objectives should be defined according to the business impact of service interruption.

  • What is backed up: database, files, configuration, logs, and release data.
  • Frequency: based on criticality and data change rate.
  • Storage: secure encrypted backup storage separated from production systems.
  • Access: restricted to authorized personnel only.
  • Recovery test: validate restoration periodically.

20. Privacy and Data Protection

ParkFlow processes user, vehicle, and potentially document-related information. The project should collect only data necessary for service delivery, set retention limits, and define procedures for correction or deletion. For Philippine-based projects, privacy obligations under the Data Privacy Act of 2012 should be reviewed with the institution’s privacy adviser.

23. Conclusion

ParkFlow Mobile App should be treated as a sensitive application because it handles identity-related data, vehicle information, parking activity, and documentation. The main risks visible in the reviewed repository are transport security weaknesses, web token exposure, and the need for stronger backend authorization and logging controls. These issues should be addressed before production use. By applying Secure SDLC principles from planning through operations and incident handling, the project can reduce risk, improve defense in depth, and better protect its users and data.
